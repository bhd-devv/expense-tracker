# Розробка й перевірки

## Порядок роботи

Спочатку прочитай наявний код, кореневий `AGENTS.md` та відповідні документи
`.agents/`. Обирай найпростіше повне рішення; не роби сторонніх рефакторингів.
Якщо код і правила розходяться, встанови причину та відобрази погоджене
рішення в документації. Не видавай заплановану архітектуру за реалізовану.

Для нового продуктового сценарію визнач:

1. Спільний backend use case, правила доступу й транзакційну межу.
2. Контракт API, ідемпотентність і поведінку при конфлікті/невідомій відповіді.
3. UX Mini App і відповідний повний сценарій у Telegram.
4. Перевірки, міграції та вплив на контейнерний деплой.

## Backend

- C# із nullable reference types, thin endpoints, feature-oriented код,
  DTO окремо від EF entities. Використовуй штатні DI, Options validation,
  logging та ProblemDetails. Не приховуй помилки порожніми `catch`.
- Передавай CancellationToken через async I/O, задавай таймаути, тримай
  транзакції короткими. Конкурентні інваріанти захищай constraints/locks.
- Authentication, Authorization, Antiforgery й Data Protection — штатні
  підтримувані механізми. Сесія, Telegram webhook і внутрішній worker мають
  різні явні межі довіри.
- Перед додаванням залежності перевір сумісність, ліцензію й підтримку.
  Фіксуй SDK у `global.json`, версії NuGet і restore lockfiles.

## Frontend

- Next.js App Router, React, strict TypeScript. Компоненти — `.tsx`, логіка
  й тести — `.ts`, ESM scripts — `.mts`, якщо підтримує runtime.
- Server Components за замовчуванням; `use client` на потрібній межі.
  Не приховуй помилки через безпідставні `any`, casts, non-null assertions
  або вимкнення type/lint checks. Залишай очевидні типи виведенню.
- UI, транспорт і предметні представлення мають різні відповідальності.
  Використовуй generated API types, не дублюй backend бізнес-правила.
  Допустима UX-перевірка форми не замінює серверну перевірку.
- Локальний стан тримай біля компонента; серверний стан — у вибраному
  механізмі fetch/cache. Не додавай global store або wrapper для кожного запиту.
- Семантичний HTML, keyboard/focus support, узгоджені loading/error/empty
  states, українська локалізація, теми Telegram й адаптивний layout.
- Не кешуй приватні відповіді в загальному Next.js cache/CDN. Auth/session
  responses — `Cache-Control: no-store`; кеш приватних даних ізолюй за сесією
  та очищай при виході/зміні користувача.
- Не додавай приховані retries mutations, зокрема через налаштування
  бібліотеки запитів. Невідома відповідь не означає відсутність операції.

## Документація та завершення

- Для великої роботи використовуй один task-файл із `.agents/templates/task.md`;
  для завершеної змістовної роботи — один changelog із
  `.agents/templates/change.md`.
- Рішення про межі сервісів, авторизацію, persistence або release записуй як
  ADR за `.agents/templates/decision.md`. Локальний баг або стилістична правка
  ADR не потребує.
- Перед завершенням запускай `python3 scripts/check_docs.py --check` і
  `git diff --check`. Після нового changelog спершу запускай
  `python3 scripts/check_docs.py --write-index`.
- У changelog/task вказуй реальні команди, результати й пропуски. Розділяй
  browser smoke, реальний Telegram, PostgreSQL-інтеграцію та Coolify.
- Не коміть, не пуш і не деплой автоматично; це окрема дія користувача,
  якщо її прямо не запитано.

## Обов'язкові перевірки за типом зміни

| Зміна | Перевірка |
| --- | --- |
| Лише документація | Зміст, узгодженість правил, Markdown і локальні посилання |
| Backend | Restore locked packages, форматування, Release build, релевантні тести |
| Frontend | Frozen install, typecheck, lint, тести за потреби, production build |
| UI-поведінка | Цільовий browser flow; Telegram-specific поведінка також у Telegram |
| Схема/транзакції | Інтеграційні тести на справжньому PostgreSQL, перевірка міграції |
| Контракт API | Генерація клієнта, перевірка відсутності drift, обидва канали |
| Deployment | Compose validation, container build, health/routing smoke test |

Команди зафіксуй у README/CI після створення відповідних проєктів. Не
вигадуй успішні build/typecheck до появи scaffold. Не пиши тести, що лише
повторюють реалізацію, для простих оборотних змін.

До першого production release перевір реальні ризикові сценарії:

- Валідний, підроблений, прострочений і повторно використаний `initData`;
  відсутній user, некоректна дата й одночасний перший вхід із двох каналів.
- Читання/зміна чужих ID, чужі inline callbacks, CSRF, завершення й
  відкликання сесії, відсутність секретів у bundle та logs.
- Повторна доставка update, подвійне підтвердження чернетки, конкурентне
  редагування, перезапуск між commit та надсиланням Telegram-повідомлення.
- Точність сум, дробові знаки валют, межі звітних дат/часових поясів,
  архівні категорії та окремі підсумки різних валют.
- Одна витрата, створена через бот, видима у Mini App, і навпаки;
  редагування, видалення й звіти також працюють через обидва канали.
- Реальна auth/cookie/CSRF поведінка в Telegram Android, iOS, Desktop і Web;
  production routing через Coolify та відновлення БД із backup.

Перед завершенням повідомляй, що змінилося, які перевірки фактично пройшли
і що залишилося неперевіреним. Створення коміту та публікація мають відповідати
поточному запиту користувача; не вважай попередній разовий коміт постійним
дозволом комітити кожну наступну зміну.
