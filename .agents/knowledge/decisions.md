# Прийняті архітектурні рішення

## ADR-019: валюта профілю як спільне позначення сум

- **Статус:** прийнято, 2026-11-02 за запитом користувача; уточнює ADR-017.
- **Контекст:** валюта задається в налаштуваннях; її зміна має змінювати
  лише позначення, зберігаючи всі введені суми.
- **Рішення:** DTO витрат, чернеток, звітів, лімітів і накопичень використовують
  `User.Currency`. Звіти та прогрес лімітів групуються лише за категорією.
  Зміна профілю не переписує записи або їхні версії. Legacy Currency та
  LimitCurrency у БД і запитах зберігаються для сумісності; нові записи
  заповнюють їх із профілю. Валютний код запиту не керує сценарієм.
  Усі позначення допускають дві дробові цифри, включно з JPY. AI не
  конвертує число й не перевизначає валюту; обидва канали прибирають вибір
  валюти витрати/ліміту/накопичення. Ідемпотентність порівнює зміст без
  legacy currency. Спільну валюту накопичень користувач підтвердив окремо.
- **Варіанти:** масове переписування валют у БД вимагало б транзакцій і
  синхронізації з довгими AI-запитами; читання профілю дає потрібну поведінку
  без міграції та втрати історичних метаданих.
- **Наслідки:** старі різновалютні числа підсумовуються без конвертації;
  backend і клієнти слід оновити узгоджено. Rollback повертає старі правила
  групування, але суми не змінює. Runtime перевірки ще не виконані.
- **Контракти:** [product](../product.md), [design](../design.md),
  [Telegram](../telegram.md), [deployment](../../docs/deployment.md).
- **Задача:** [компактність і валюта](../tasks/compact-layout-currency-2026-11-02/README.md).

Це короткий індекс ADR для рішень, що змінюють межі сервісів, авторизацію,
зберігання даних або release-процес. Звичайні баги й локальні UI-правки ADR
не потребують.

## ADR-001: бот і API в одному ASP.NET Core backend

- **Статус:** замінено ADR-007 від 2026-11-01; нижче збережено попереднє
  рішення для історії, воно більше не визначає архітектуру.
- **Контекст:** Mini App і Telegram-бот мають виконувати однакові сценарії
  та застосовувати однакові ownership/business rules.
- **Рішення:** webhook, bot handlers, HTTP API та прикладні сценарії живуть в
  одному backend; бот не викликає власний API через внутрішній HTTP.
- **Наслідки:** один source of truth для правил і транзакцій; handlers мають
  залишатися тонкими; масштабування worker-ів потребує окремого контролю.

## ADR-002: один публічний origin для Mini App і API

- **Статус:** прийнято.
- **Контекст:** потрібна безшовна cookie-сесія без передачі bearer token у URL.
- **Рішення:** Coolify маршрутизує `/api/*` до backend, решту UI до Next.js
  на тому самому HTTPS origin. Відповідно до ADR-007 webhook спрямовується
  до aiogram-сервісу; приватні bot endpoints через публічний proxy недоступні.
- **Наслідки:** простіші cookies/CSRF та frontend requests; routing треба
  перевіряти під час deployment smoke, а API не має потрапляти в catch-all.

## ADR-003: cookie-сесія після перевірки Telegram Mini App proof

- **Статус:** прийнято.
- **Контекст:** `initData` доводить запуск із Telegram, але не має бути
  довготривалим browser bearer token.
- **Рішення:** backend перевіряє `initData`, створює серверну сесію у
  `HttpOnly` cookie та захищає state-changing requests Antiforgery.
- **Наслідки:** потрібні Data Protection keys, session persistence і реальна
  перевірка Telegram-клієнтів; localStorage для auth не використовується.

## ADR-004: PostgreSQL authoritative для inbox/outbox і діалогів

- **Статус:** прийнято.
- **Контекст:** Telegram повторює updates, бот має чернетки й side effects,
  а restart контейнера не повинен втрачати стан.
- **Рішення:** PostgreSQL зберігає updates, conversation drafts, sessions,
  idempotency keys та outbox; Redis/пам'ять не є джерелом бізнес-стану.
- **Наслідки:** потрібні constraints, короткі транзакції, claim/locking,
  worker retry policy та міграції. Telegram delivery не є exactly-once.

## ADR-005: історія не перевизначає чинні контракти

- **Статус:** прийнято.
- **Контекст:** task, research і changelog накопичують корисний контекст, але
  можуть описувати старий код або вже скасоване рішення.
- **Рішення:** чинним джерелом є правила/knowledge, а історичні документи
  лише посилаються на них і не дають дозволу виконувати операції.
- **Наслідки:** перед роботою треба звірити документ із кодом і актуальним
  користувацьким запитом; суперечність виправляється в поточному контракті.

## ADR-006: AI-обробка повідомлень через OpenRouter на backend

- **Статус:** прийнято, 2026-11-01; адаптер реалізовано, live provider ще не перевірено.
- **Контекст:** користувач визначив OpenRouter provider для транскрипції
  голосових повідомлень і автоматичного вибору категорії витрати.
- **Варіанти:** прямі інтеграції з іншими AI providers або локальна
  транскрипція не обрані, оскільки виходять за поточну вимогу. Browser-side
  виклик із provider key непридатний через розкриття серверного секрету.
- **Рішення:** .NET backend виконує AI-обробку й валідує її результат.
  Продуктовий контракт описано в [product.md](../product.md); він є єдиним
  джерелом правил введення, дати й категорії.
- **Наслідки:** перед реалізацією треба вибрати й перевірити сумісні моделі
  та audio formats, обмежити витрати/таймаути, забезпечити приватність
  повідомлень і видалення тимчасового аудіо. Інтеграція не змінює identity,
  ownership або вимогу підтвердження фінансової операції.

## ADR-007: окремий Python/aiogram адаптер для Telegram

- **Статус:** прийнято, 2026-11-01; замінює ADR-001. Реалізовано й локально перевірено.
- **Контекст:** користувач прямо обрав aiogram і мінімум boilerplate, а
  основний backend залишається C# / ASP.NET Core.
- **Варіанти:** .NET Telegram-клієнт у тому самому процесі не відповідає
  вибору aiogram; перенесення бізнес-логіки в Python створило б другий
  backend і дублювання правил.
- **Рішення:** окремий aiogram 3.x сервіс для webhook, routers, кнопок та
  Telegram delivery. Він працює через приватний .NET API з окремим service
  credential. .NET залишається єдиним власником сценаріїв, БД та OpenRouter.
- **Наслідки:** у Compose потрібний bot container і Python lockfile;
  контракт, actor scope, retries та leases перетинають межу процесів.
  Спільна транзакція між сервісами відсутня, тому потрібні durable
  inbox/outbox та ідемпотентність. Redis або broker для цього не додаються
  без окремої потреби.
- **Чинні контракти:** [architecture.md](../architecture.md),
  [security.md](../security.md), [telegram.md](../telegram.md),
  [deployment.md](../deployment.md). Цей ADR фіксує причину вибору,
  а детальні протоколи підтримуються у відповідних контрактах.

## ADR-008: один Caddy gateway перед трьома application services

- **Статус:** прийнято та локально перевірено, 2026-11-01.
- **Контекст:** Coolify повинен відкривати один origin і тільки публічні
  маршрути API/бота; специфічні labels proxy залежать від інсталяції Coolify.
- **Варіанти:** окремі path routers у Coolify або один явний gateway.
- **Рішення:** у Compose публічний лише gateway. Caddy маршрутизує Next.js,
  `/api/*` і webhook; `/internal/*` повертає 404. TLS завершує Coolify.
  Короткі фінансові/catalogue мутації серіалізуються advisory lock власника;
  він не утримується під час AI/Telegram I/O.
- **Наслідки:** ще один невеликий контейнер і контрольований private IP;
  правила маршрутизації версіонуються в репозиторії й копіюються в gateway
  image через `deploy/gateway.Dockerfile`. Host bind mount Caddyfile не
  використовується: Coolify helper checkout і filesystem Docker host
  можуть відрізнятися. API upstream використовує alias
  `expense-tracker-api-private` лише в private network, щоб додаткова мережа
  Coolify не змінила source IP gateway і перевірку trusted proxy.
  Зміна routing потребує перебудови gateway. HTTPS і Telegram
  клієнти потребують перевірки після справжнього deployment.
- **Контракт запуску:** [deployment](../../docs/deployment.md).

## ADR-009: нормалізація голосу перед OpenRouter

- **Статус:** реалізовано, 2026-11-01; live audio model не перевірено.
- **Контекст:** Telegram надсилає OGG/Opus, браузер може надсилати WebM/MP4;
  підтримка форматів відрізняється між OpenRouter models/providers.
- **Рішення:** ffmpeg на backend нормалізує дозволені audio containers у
  mono WAV 16 kHz. Ліміти — 10 МБ і 120 с; тимчасові файли очищаються.
  Chat Completions отримує base64 `input_audio` і strict JSON schema для
  транскрипції. Далі транскрипт обробляє текстова модель за ADR-010.
  Model IDs версіонуються у серверному конфігу.
- **Наслідки:** frontend і бот не мають provider credentials або власних
  правил транскрипції. Потрібні ffmpeg у runtime image, явна згода
  користувача й перевірка реальної моделі до release.

## ADR-010: фіксовані AI-моделі та окремий STT перед текстовим розбором

- **Статус:** прийнято, 2026-11-01; уточнює ADR-009 за запитом користувача.
- **Контекст:** користувач обрав найновішу GPT Luna для тексту та якісну
  бюджетну модель STT для української й англійської; ID мають бути в конфігу.
- **Варіанти:** одна audio-модель для всього голосового сценарію не
  застосовувала б Luna до голосових витрат. Окремі provider SDK або прямий
  STT provider поза OpenRouter не потрібні.
- **Рішення:** `openai/gpt-6-luna` і `google/gemini-3.1-flash-lite` у
  [appsettings.json](../../src/backend/ExpenseTracker.Api/appsettings.json).
  STT отримує лише аудіо; Luna — текст/транскрипт та каталог категорій.
  Обидва виклики — на backend через OpenRouter, з strict JSON schema,
  `require_parameters` і `data_collection=deny`, під спільним timeout 75 с.
  Luna не отримує непідтримуваний `temperature`, reasoning — `none`;
  Flash-Lite використовує `minimal`. Немає автоматичного fallback/retry.
- **Доказ вибору:** [офіційна сторінка Luna](https://developers.openai.com/api/docs/models/gpt-6-luna),
  [каталог OpenRouter](https://openrouter.ai/api/v1/models),
  [Gemini 3.1 Flash-Lite](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/gemini/3-1-flash-lite)
  та [аудіоформати OpenRouter](https://openrouter.ai/docs/guides/overview/multimodal/audio).
  Перевірено 2026-11-01; каталог підтверджує audio input і structured outputs,
  Google описує покращення ASR та minimal thinking. За каталогом audio input
  Flash-Lite коштує $0.50/1M tokens, output — $1.50/1M; це не фіксована
  ціна хвилини. Якість uk/en і доступ конкретного ключа ще не перевірено.
- **Наслідки:** голос має два послідовні provider-запити; STT failure зупиняє
  обробку до Luna. API, bot DTO, фінансові інваріанти й БД сумісні,
  міграція не потрібна. У env залишається лише секретний API key.
  Чинний продуктовий контракт — [product.md](../product.md).

## ADR-011: атомарне демонаповнення з окремим записом виконання

- **Статус:** `accepted`, 2026-11-01.
- **Контекст:** `/seed` має додати витрати за жовтень лише поточному actor,
  витримати повторну доставку/конкурентні виклики й не відновлювати записи,
  які користувач уже відредагував або видалив.
- **Варіанти:** пошук за описом ненадійний після редагування; перевикористання
  draft/inbox змішує різні сценарії й строки зберігання. Обрано малу таблицю
  `DemoSeeds` з ключем `(UserId, Period)`, кількістю й UTC часом виконання.
- **Рішення:** приватний BotActor endpoint викликає backend `DemoSeedService`.
  User advisory lock і одна PostgreSQL transaction охоплюють перевірку
  запису виконання, ліміту категорій та витрати. Після ADR-013 seed не
  створює фінансові рахунки, валюта вказана безпосередньо в демовитраті.
  Використовується спільний `ExpenseService.Apply`, без дублювання грошових
  і ownership-правил у Python. Повтор повертає `createdCount=0`.
- **Наслідки:** потрібна additive migration `AddDemoSeeds` перед backend;
  rollback застосунку не вимагає видалення таблиці. Видалення запису виконання
  вручну зніме захист від повторного наповнення. Звичайні витрати доступні
  через обидва канали; bot DTO генеруються з OpenAPI. Профіль і персональні
  дані не переписуються, AI/outbox не викликаються. Наповнення лише за явною
  командою, без автоматичного seed у міграції або startup.
- **Контракти:** [product.md](../product.md), [telegram.md](../telegram.md).
- **Задача:** [демовитрати за жовтень](../tasks/seed-october-2026-11-01/README.md).

## ADR-012: console logs і persistent щоденні архіви через спільний runner

- **Статус:** прийнято, 2026-11-01; container/Coolify smoke ще не виконано.
- **Контекст:** потрібні всі серверні дії та помилки в Coolify і файли зі
  щоденною ротацією, що переживають перевипуск контейнерів.
- **Рішення:** Python stdlib runner у runtime images синхронно дублює
  stdout/stderr у Docker console й окремий service volume; UTC midnight
  rotation, gzip, retention за кількістю та календарним віком. Сервіси
  самі формують безпечні події; runner не читає Docker socket і не додає
  зовнішньої служби. .NET logging queue чекає замість відкидання подій.
- **Альтернативи:** різні file sinks у кожному runtime дублюють policy;
  Docker log rotation сама не забезпечує добові архіви між redeploy.
- **Наслідки:** Python додано у backend/frontend/gateway/PostgreSQL runtime
  images; bot уже використовує Python. PostgreSQL base/version і data volume
  збережені. Runner передає сигнали та exit code; Compose має init і grace
  period. Один writer на service volume вимагає stop-first release;
  для replicas потрібні окремі файли/volumes або collector. Файли не є
  транзакційним audit ledger чи backup і не гарантують захист від втрати диска.
- **Безпека:** без HTTP bodies, query, tokens, сум, нотаток і transcripts.
  Stack locations/types зберігаються без довільних exception messages/SQL;
  gateway filters і runner redaction додають захист. Retention початково
  14 днів, `LOG_RETENTION_DAYS=1..365`. Докладно: [logging](../../docs/logging.md).

## ADR-013: витрати без фінансових рахунків і надходжень

- **Статус:** прийнято, 2026-11-02; реалізовано локально, runtime перевірки не запускалися.
- **Контекст:** користувач прибрав фінансові рахунки з продукту. Є один
  Telegram-акаунт користувача та його витрати; обліку надходжень і балансів немає.
- **Рішення:** видалити Account, DefaultAccountId, посилання й фільтри з
  backend, Mini App та бота. Валюта зберігається безпосередньо у витраті й
  чернетці. Нова чернетка отримує валюту профілю; явно вказана підтримувана
  валюта або ручна зміна має пріоритет. Зміна профілю не конвертує історію.
  Seed створює лише витрати й потрібні категорії, зберігаючи DemoSeeds receipt.
- **Альтернатива:** приховування сторінки зі збереженням обов'язкового рахунку
  залишило б зайву залежність у моделі та API, що суперечить спрощенню.
- **Наслідки:** міграція RemoveFinancialAccounts зберігає витрати та переносить
  валюту чернеток до видалення каталогу. Bot conversation reset і нові версії
  чернеток захищають від старих кроків. Потрібні backup та stop-first release
  backend/bot/frontend; старі клієнти треба повторно відкрити. Down відхиляється,
  відновлення старої моделі потребує backup із відповідними images.
- **Контракти:** [product](../product.md), [deployment](../../docs/deployment.md).
- **Задача:** [витрати без рахунків](../tasks/expenses-without-accounts-2026-11-02/README.md).

## ADR-014: спільний режим введення й явна дата в AI-описі

- **Статус:** прийнято, 2026-11-02; реалізовано локально, runtime перевірки не запускалися.
- **Контекст:** користувач запросив ручний/AI-перемикач для Mini App і бота
  та пріоритет дати у формі або текстовому/голосовому описі над сьогодні.
- **Рішення:** `User.InputMode` (`manual` / `ai`) зберігається у PostgreSQL;
  це UX-налаштування, окреме від `AiConsent`. Початкове `ai` зберігає чинний
  сценарій. Обидва канали використовують `ExpenseService.Create` і те саме
  ідемпотентне підтвердження; ручна чернетка відразу `ready`, без provider I/O.
  `CreateDraftRequest.mode` необов'язковий: без нього діє режим профілю.
  Явний режим дозволяє завершити повтор зі збереженим способом введення.
- **Дата:** backend фіксує локальну опорну дату перед AI, передає її лише
  моделі розбору й перевіряє ISO-дату у відповіді. Відносна дата обчислюється
  AI від цієї опори, без згадки лишається сьогодні. Некоректна/неоднозначна
  явна дата очищає придатну до збереження дату чернетки: службове `0001-01-01`
  відхиляється підтвердженням, клієнти вимагають вибір. Ручне виправлення
  має пріоритет; identity, ownership і суми залишаються серверними.
- **Альтернатива:** локальний перемикач у кожному клієнті розсинхронізує
  канали; окремий manual CRUD дублює правила й ідемпотентність.
- **Наслідки:** additive migration `AddInputMode`, additive profile/request
  fields, синхронізовані OpenAPI/DTO. Міграцію застосувати перед новим backend,
  потім оновити обидва клієнти. Уже створені чернетки не перерозбираються.
  Down видаляє лише налаштування режиму; звичайний image rollback не
  потребує видалення колонки. Живе AI-розпізнавання дат ще не перевірено.
- **Контракти:** [product](../product.md), [Telegram](../telegram.md),
  [deployment](../../docs/deployment.md).

## ADR-015: спільний каталог і збереження іконок категорій

- **Статус:** прийнято, 2026-11-02; реалізовано локально, runtime перевірки не запускалися.
- **Контекст:** потрібен широкий вибір іконок і зміна іконки незалежно від
  назви категорії з однаковим результатом у Mini App і боті.
- **Рішення:** nullable `Category.Icon` зберігає стабільний ID зі списку
  backend. Вбудований JSON містить 100 іконок у 10 групах, uk/en назви й
  emoji для Telegram; authenticated `/category-icons` доступний обом каналам.
  Mini App використовує явні імпорти наявної Lucide 1.66.0 (ISC).
  Backend перевіряє ID, ownership і version. Пропущений/null icon зберігає
  чинне значення; fallback за code фіксується до перейменування категорії.
- **Альтернатива:** SVG uploads/зовнішні URL потребують окремої моделі
  зберігання й перевірки та не потрібні для готового каталогу. Окремі списки
  назв/груп у клієнтах створили б розбіжності між каналами.
- **Наслідки:** additive migration `AddCategoryIcons` додає nullable text
  без переписування даних. Застосувати перед backend, потім оновити клієнти.
  Старі клієнти не скидають вибір; старі bot callbacks проходять чинні
  version checks. Новий `category_icon` діалог слід завершити або скинути
  перед поверненням до старого bot image. Rollback сумісних images може
  залишити колонку; Down видаляє лише вибрані іконки.
- **Контракти:** [product](../product.md), [design](../design.md),
  [Telegram](../telegram.md), [deployment](../../docs/deployment.md).
- **Задача:** [каталог іконок](../tasks/category-icons-2026-11-02/README.md).

## ADR-016: явне видалення категорій без каскаду витрат

- **Статус:** прийнято, 2026-11-02; локальна реалізація, runtime не перевірено.
- **Контекст:** видалення категорій і витрат потрібне безпосередньо у
  списках; користувач прибрав кнопку архівації категорій.
- **Рішення:** спільний `CatalogService.Delete` і DELETE endpoint для
  обох каналів фізично видаляють лише категорію без витрат і активних
  непрострочених чернеток. `category_in_use` пояснюється обома клієнтами.
  Ownership, version та перевірка посилань виконуються під тим самим
  user lock, що й зміни витрат; FK Restrict збережений. Підтвердження — у
  UI перед запитом; бот перевіряє версію до показу й перед видаленням.
- **Альтернативи:** каскад витрат змінював би історію й звіти без окремого
  запиту; новий soft-delete стан потребував би схеми й правил відновлення.
- **Наслідки:** без нової міграції; backend оновлюється перед клієнтами.
  Legacy archive API/дані зберігаються, кнопок archive/restore немає;
  старі archive callbacks відхиляються. Успішне видалення не скасовується
  image rollback. Видалені дані не відновлюються автоматично.
- **Контракти:** [product](../product.md), [Telegram](../telegram.md),
  [deployment](../../docs/deployment.md).
- **Задача:** [видалення у списках](../tasks/inline-delete-2026-11-02/README.md).

## ADR-017: місячний ліміт категорії з однією валютою

- **Статус:** прийнято, 2026-11-02; реалізовано локально, runtime не перевірено.
- **Контекст:** потрібні сума ліміту та прогрес категорії в обох каналах,
  без змішування валют і дублювання фінансових правил у клієнтах.
- **Рішення:** nullable `Category.MonthlyLimit` (`numeric(20,4)`) та
  `LimitCurrency` із pair/positive constraint. Один ліміт на категорію;
  поточний календарний місяць/timezone власника, без збереження історії
  бюджетів. Окремий PUT `/categories/{id}/limit` із ownership/version та
  user lock встановлює/прибирає ліміт. Назва/іконка його не переписують.
  Каталог повертає computed DTO із грошовими рядками, decimal-відсотком,
  точним exceeded і датами. Один grouped query рахує місячні витрати в
  кожній категорії/валюті; клієнти лише форматують і обрізають ширину смужки.
- **Альтернативи:** FX потребував би джерела курсів і фінансової політики;
  окрема таблиця budget periods/історія не потрібна для поточного місячного
  сценарію. Обчислення у frontend/bot розійшлися б на датах і точності.
- **Наслідки:** additive migration `AddCategoryLimits` перед backend, потім
  обидва клієнти. Початково limit null. Старі DTO/rename/icon запити сумісні.
  Прогрес змінюється після редагування/видалення витрат, місяця або timezone;
  перевищення не блокує запис. Перед rollback старого bot image завершити
  нові limit діалоги; Down видаляє лише налаштування лімітів.
- **Контракти:** [product](../product.md), [design](../design.md),
  [Telegram](../telegram.md), [deployment](../../docs/deployment.md).
- **Задача:** [ліміти категорій](../tasks/category-limits-2026-11-02/README.md).

## ADR-018: окремі накопичувальні рахунки

- **Статус:** accepted, 2026-11-02; локальна реалізація, runtime не перевірено.
- **Контекст:** користувач запросив створення рахунків, поповнення й списання
  через окрему сторінку з головної. Це розширює ADR-013: звичайні витрати
  залишаються без account FK, але з'являється незалежний журнал накопичень.
- **Варіанти:** повернення старої обов'язкової Account-моделі змінило б
  звичайні витрати. Окремий Savings feature додає запитаний сценарій без
  переписування expense history чи категорій.
- **Рішення:** SavingsAccounts + append-only SavingsEntries, позначення валюти
  з налаштувань профілю, decimal totals і суми, composite ownership FK. Owner lock,
  DB constraints, atomic totals+entry, request ID та порівняння незмінних
  полів захищають конкурентні списання й дублі. Спільний .NET use case
  обслуговує обидва канали; AI, перекази й FX відсутні.
- **Наслідки:** additive `AddSavingsAccounts` перед новим backend, потім
  frontend/bot. Стара expense API сумісна; нові bot dialogs треба завершити
  перед rollback bot image. Нові таблиці зберігаються при image rollback;
  Down навмисно відхиляє видалення фінансового журналу.
- **Контракти:** [product](../product.md), [architecture](../architecture.md),
  [Telegram](../telegram.md), [deployment](../../docs/deployment.md).
- **Задача:** [накопичення](../tasks/savings-accounts-2026-11-02/README.md).

## ADR-019: регулярні завдання лише в окремому вебзастосунку

- **Статус:** accepted, 2026-11-03; локальна реалізація, runtime не перевірено.
- **Контекст:** користувач явно запросив інший Web App із регулярними
  завданнями й лише кнопкою відкриття в боті. Це виняток із parity витрат.
- **Варіанти:** другий deployment/domain додав би зайві routing/auth/secrets;
  bot task CRUD суперечив би прямій вимозі. LocalStorage як основне сховище
  втрачало б спільність пристроїв і серверну ownership-перевірку.
- **Рішення:** окремий `/tasks` у чинному Next.js та browser-only .NET
  feature, спільна перевірена Telegram cookie session/CSRF і PostgreSQL.
  `RecurringTasks` + `TaskCompletions`, fixed cadence 1/2/3/7 від старту,
  timezone власника, owner lock, version і composite ownership PK/FK.
  Перейменування не змінює розклад. Видалення приховує завдання, резервує
  його ID та зберігає історію без UI відновлення. Створення дедуплікується
  ID; versioned повтори можуть повернути conflict. Невідома відповідь
  потребує явної дії з тим самим збереженим запитом, без auto retry.
- **Наслідки:** additive `AddRecurringTasks` перед backend, потім frontend
  і bot. Поточні фінансові контракти/таблиці не змінюються. `/start` оновлює
  reply-кнопки, старі inline launch продовжують відкривати витрати.
  Image rollback зберігає нові таблиці; Down відхилено для збереження історії.
- **Контракти:** [product](../product.md), [architecture](../architecture.md),
  [Telegram](../telegram.md), [deployment](../../docs/deployment.md).
- **Задача:** [вебзастосунок завдань](../tasks/recurring-tasks-2026-11-03/README.md).

## ADR-020: Telegram-бот лише відкриває два Web Apps

- **Статус:** accepted, 2026-11-04; реалізовано локально, runtime не перевірено.
- **Контекст:** користувач прямо скасував команди й усю пов'язану логіку;
  бот має лише дві кнопки відкриття витрат і завдань. Це замінює попередню
  вимогу channel parity та launch UX із ADR-019.
- **Рішення:** два inline `web_app` посилання `/` і `/tasks` для signed
  initData. Будь-яке private human message лише показує меню й прибирає
  стару reply keyboard. Мова меню з Telegram, без читання профілю.
  Command/callback/dialog/seed/audio/finance handlers, outbox worker,
  notification creation та private actor workspace routes видалені.
  Service auth дає лише `service=bot`; довільний actor header ігнорується.
  Залишено мінімальний durable inbox із dedupe/lease для доставки меню.
  Python DTO генеруються лише з private delivery OpenAPI.
- **Альтернативи:** приховати кнопки, залишивши actor API й фінансові
  handlers, не виконало б запит про видалення логіки. Повне видалення inbox
  змінило б надійність webhook і не потрібне для цього сценарію.
- **Persistence:** Conversation/DemoSeed та історичні outbox записи лишаються
  сумісним неактивним сховищем. Destructive migration немає. Старі витрати,
  демодані, накопичення й завдання не видаляються. Legacy bot draft можна
  підтвердити у Web App без Telegram-сповіщення.
- **Release:** зупинити старий bot worker, узгоджено оновити backend/бота,
  явно виконати register-webhook: message-only, pending зберігаються,
  default/all-private command menus для default/uk/en очищуються,
  додатковий menu Web App скидається. Старі callbacks не виконують дій.
  Rollback потребує сумісної пари images; повернення старого outbox worker
  може доставити старі queued notifications, тому потребує перегляду черги.
- **Контракти:** [Telegram](../telegram.md), [security](../security.md),
  [architecture](../architecture.md), [deployment](../../docs/deployment.md).
- **Задача:** [бот із двома кнопками](../tasks/launcher-only-2026-11-04/README.md).

## ADR-021: окремі доходи й категорії доходів

- **Статус:** accepted, 2026-11-05, за прямим запитом користувача.
- **Контекст:** потрібна сторінка доходів замість звітів у навігації й
  незалежні категорії доходів зі сторінкою керування.
- **Варіанти:** спільний тип Expense/Category із discriminator вимагав би
  змін усіх існуючих AI/звітних запитів. Окремі таблиці зберігають чинні
  expense інваріанти й явно виключають доходи зі звітів витрат.
- **Рішення:** browser-only .NET feature, `IncomeCategories` + `Incomes`,
  decimal суми, composite ownership FK, owner lock, version. Створення
  атомарно зберігає request ID та hash; логічне видалення резервує ID.
  Редагування й видалення приймають точний повтор останньої операції,
  інакше повертають conflict. Позначення валюти з профілю, без конвертації.
- **Сумісність:** additive `AddIncomes` перед backend/frontend; нових
  secrets, сервісів і bot контрактів немає. Старі клієнти витрат сумісні.
  Image rollback зберігає таблиці, Down відхилено. Міграція перевірена
  лише в ізольованій локальній PostgreSQL 14; production/Coolify не змінені.
- **Контракти:** [product](../product.md), [architecture](../architecture.md),
  [deployment](../../docs/deployment.md).
- **Задача:** [доходи](../tasks/incomes-2026-11-05/README.md).

## ADR-022: видалення накопичувальних рахунків із version і tombstone

- **Статус:** accepted, 2026-11-05, за прямим запитом користувача.
- **Контекст:** кошик має бути видимим як у списках інших фінансових записів;
  видаляти потрібно також створені рахунки з історією та залишком.
- **Варіанти:** фізичне каскадне видалення втратило б request ID й дозволило
  старому create retry відновити рахунок. Відмова для непорожніх рахунків
  не виконала б запит про видалення створених рахунків.
- **Рішення:** `SavingsAccounts.Deleted` і `Version`, DELETE із підтвердженою
  version та owner lock. Новий entry збільшує version; stale delete повертає
  409. Exact retry успішного delete повертає 204. Tombstone приховує всі
  читання/записи рахунка, зберігаючи службовий журнал та зарезервований ID.
- **Release:** additive `AddSavingsDeletion`; нових env/сервісів немає.
  Зупинити старий backend до запуску нового: він не збільшує version і
  ігнорує Deleted. Frontend оновлюється після нового API. Після першого
  видалення rollback допустимий лише на deletion-aware backend; старий
  image поверне приховані рахунки до списку. Down відхилено. Бот не змінено.
- **Контракти:** [product](../product.md), [architecture](../architecture.md),
  [deployment](../../docs/deployment.md).
- **Задача:** [видалення рахунків](../tasks/delete-savings-2026-11-05/README.md).
