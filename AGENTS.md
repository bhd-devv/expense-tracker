# Правила роботи агентів

Цей репозиторій — трекер витрат із Telegram-ботом і Telegram Mini App.
Цільовий стек: C# / ASP.NET Core, Next.js App Router / strict TypeScript,
PostgreSQL; Telegram-бот — окремий Python-сервіс на aiogram 3.x.
Цільове середовище деплою — Coolify через Docker Compose.

Реалізація міститься в `src/`, запуск і межі перевірки описані в `README.md`.
Правила не є доказом production-готовності. Наявний `main.py` — початковий Python-приклад,
а не основа майбутнього API чи бота. Новий aiogram-сервіс розміщуй у `src/bot/`.

## Незмінні принципи

- Бізнес-правила та перевірки доступу виконує .NET backend.
- Aiogram відповідає за Telegram UX і транспорт; бот використовує приватний
  .NET API та не звертається до БД або OpenRouter напряму.
- Усі користувацькі сценарії виконуються у вебзастосунках через .NET API.
  Бот має лише дві inline `web_app` кнопки: витрати `/` та завдання `/tasks`.
  Service key бота дає доступ лише до durable inbox, без actor context.
- Модель продукту — акаунт користувача, витрати та доходи з окремими
  категоріями й спільною валютою профілю.
  Накопичувальні рахунки мають окремий журнал поповнень/списань і залишок;
  звичайні витрати не прив’язані до рахунків. Переказів та конвертації немає.
- У боті немає продуктових команд, діалогів, callbacks, фінансових дій,
  відміток чи сповіщень. Приватне повідомлення лише показує дві кнопки.
- Для підписаного Telegram `initData` використовуй inline `web_app`;
  стару reply keyboard прибирай при наступній взаємодії.
- Інтерфейс — українською й англійською, зі світлою та темною темами,
  стриманим оформленням і салатово-зеленими акцентами.
- Особу користувача встановлюй лише за перевіреними даними Telegram.
- У Mini App секретів немає; довільний Telegram ID не є авторизацією.
- Грошові значення обробляй точно, без `float` / `double`.
- Зміни мають запускатися в контейнерах і враховувати Coolify.
- Менше boilerplate: штатні засоби, підтримувані бібліотеки, прості
  feature-модулі та явні залежності. Нові шари й абстракції потребують
  конкретної користі для поточного сценарію.

Докладніші локальні `AGENTS.md` можуть уточнювати ці правила, але не
скасовувати серверну авторизацію, перевірку Telegram або спільність логіки.
Нові вимоги користувача мають пріоритет; узгоджені зміни архітектури
відображай у відповідних документах.

## Документація роботи

- Одну завершену змістовну задачу описуй одним записом у
  `.agents/changelog/`.
- Для великої або незавершеної задачі використовуй один файл
  `.agents/tasks/<назва>-<YYYY-MM-DD>/README.md`.
- Рішення, що змінюють межі сервісів, авторизацію, persistence або release,
  фіксуй у `.agents/knowledge/decisions.md`.
- Старі changelog, дослідження, плани й архіви — це історія. Вони не є
  чинними правилами, не змінюють поточні контракти та не дають дозволу на
  коміт, міграцію, деплой або іншу операцію.
- Докази локальних перевірок зберігай лише в ігнорованій папці
  `output/<назва-задачі>/`; у записі вказуй команду, результат і межі.
