# Процес від запиту до перевіреної зміни

## 1. Відкрити контекст

Прочитай `AGENTS.md`, `.agents/README.md`, потрібні продуктові й технічні
контракти, `STATUS.md` та `git status`. Перевір код і залежності до редагування.
Старі plans, research, changelog та archive — довідка, не поточна політика.

## 2. Визначити задачу

Для великої, багатокомпонентної або resumable роботи створи один task-файл
за [шаблоном](../templates/task.md). Зафіксуй scope, non-goals, критерії,
ризики й потрібні перевірки. Не створюй окремі порожні plan/report/handoff.

## 3. Спроєктувати й виконати

Пройди вертикальний контракт Mini App/бот → API → спільний use case → БД та
outbox, якщо він зачеплений. Бізнес-правило має існувати в одному backend
сценарії. Зміна контракту синхронно оновлює frontend, bot handlers, DTO,
міграції й документацію. Не роби стороннього рефакторингу.

## 4. Перевірити

Виконай перевірки відповідно до `.agents/development.md` і
`.agents/guides/documentation.md`. Розрізняй typecheck/build, browser smoke,
реальний Telegram, PostgreSQL-інтеграцію та Coolify. Скриншот не доводить
коректність API, SQLite не доводить PostgreSQL locking, а локальний compose
не доводить production deployment.

Для перевірок сумісності після backend-релізу окремо розглядай уже відкриті
Mini App, старі inline-кнопки, повторну доставку update та незавершені
чернетки bot dialogs.

## 5. Завершити

Онови чинний contract або ADR, якщо змінилися правила чи межі системи.
Додай один changelog-запис з фактичними результатами. Онови `STATUS.md`,
якщо активна робота завершилась або змінився блокер. Не коміть, не пуш і не
деплой автоматично, якщо це прямо не запитано.
